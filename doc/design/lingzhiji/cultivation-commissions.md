# 灵植堂委托设计（M6b）

## 1. 需求追溯

- 关联需求：REQ-LINGZHIJI-COMMISSION-001
- 覆盖：月度委托生成、接取、交付、放弃、存档恢复及定额库存预览。
- 未覆盖：NPC 好感、图鉴、加工配方、灵草育种和委托专属场景。

## 2. 契约引用

- 不新增外部接口。
- 状态归属 `GameState`，最终字段以 `src/game/types.ts` 为事实来源。
- 委托需要新增持久状态。T33 正在落 v4 存档迁移，本功能须等 T33 完成后追加 v4→v5；不得并行改写同一迁移链。

## 3. 技术设计

### 3.1 职责与数据流

```text
月初日结算 → 生成本月选项并保存
玩家接取 → engine 校验本月资格，写入活跃委托
玩家交付 → 校验库存，原子扣草、发奖励、记录日志
玩家放弃 → 清除活跃委托，本月资格保持已用
页面刷新/导入 → save 迁移与校验恢复合法委托状态
```

- 月份变化与委托生成挂在既有日推进管线；不改随机事件、生长、缺水和月末定额的先后顺序。
- 选项由当前境界可播种的灵草候选池构成；顺序固定且结果写入存档，刷新不重抽。
- 交付动作复用库存与现有资源出口；先完整校验，再一次性扣除目标灵草并发奖励。
- 交付预览复用当前仓库与月度定额折算口径；不改变定额算法。
- 奖励暂限灵石、贡献、心得或种子，不增加新资源类型。具体表格经确认后再模拟校准。

### 3.2 状态流转

```text
本月未接取 ──接取──► 活跃委托 ──交付──► 已完成
      │                  │
      └─跨月刷新选项      └─放弃──► 本月已接取（不再接其他）
```

- 每月最多接取一次；活跃委托允许跨月保留。
- 未接取的委托选项在下月刷新；活跃委托不因刷新而被覆盖。
- 完成与放弃均清除活跃委托，本月接取资格仍保持已用。
- 接取、交付和放弃均为 0 AP；不影响每日任务堂完成门控。

### 3.3 存档与校验

- 新增当前月选项、当月接取标记和可选活跃委托三类状态。
- v4→v5 迁移为旧档补空委托状态；由 T33 的 v4 实现完成后追加，保持单一迁移链。
- 导入校验：月份、委托目标灵草、正整数数量、奖励范围和选项数量必须合法；非法状态整份导入失败，不部分恢复。
- 活跃委托交付使用当前库存，不另记 harvest counter，避免引入第二套收获账本。

### 3.4 页面原型（阶段 0 示意，尚非确认后的沉淀型原型）

```text
┌ 灵植堂委托 · 第 3 月 ──────────────────────────┐
│ 宗门定额储备：12 / 15 株当量                    │
│ ┌ 委托一：凝露花 ×4     奖励：贡献 +?   [接取] ┐ │
│ └ 委托二：青灵草 ×6     奖励：灵石 +?   [接取] ┘ │
│                                                  │
│ 空状态：本月委托已接取 / 暂无可接委托             │
│ 活跃：交付凝露花 ×4 · 当前仓库 3 株                │
│ 交付预览：库存 −4 · 定额储备 12 → 8 株当量        │
│ [交付]（库存不足时禁用并写明缺少数量） [放弃]      │
└──────────────────────────────────────────────────┘
```

- 入口放入既有 `ActionPanel`，委托内容使用单个游戏内弹层，不新增场景或路由。
- loading：本地同步读写，无独立 loading 态；若后续有异步来源，再单独设计。
- empty：显示当月已接取或无可接委托的原因，并给出下一月刷新说明。
- error：委托状态校验失败时提示「委托数据无效，请导入有效存档」，不清空玩家存档。
- 条件不足：接取资格已用、库存不足时按钮禁用并显示具体原因。
- 无权限：本作无权限模型；不额外设计权限状态。

## 4. 交互与异常

| 场景 | 处理 |
|---|---|
| 月初生成选项 | 只取当前境界可播种的灵草，固定顺序并随游戏状态保存 |
| 已有活跃委托 | 禁用其他接取按钮，提示先交付或放弃 |
| 库存不足 | 展示缺口，交付动作不产生任何副作用 |
| 交付会影响定额 | 二次确认区显示扣除后的定额储备，玩家主动确认 |
| 月份推进 | 未接取选项刷新；活跃委托保留；接取资格重置 |
| 刷新/导入存档 | 从存档恢复委托；迁移与结构校验失败时拒绝载入 |

## 5. 阶段 1 原型与验证计划

- 选型：技术栈已定且页面方向明确，按 `frontend-AGENTS.md` 采用正式工程内的沉淀型真栈原型；原型使用 Fake 数据，不连接游戏引擎。
- 原型位置：`src/components/` 的委托入口与弹层最终路径；具体文件由实现服务在阶段 1 创建并登记。
- 用户确认委托弹层布局、交付预览和条件不足态后，才接入真实 `GameState` 与引擎动作。
- Vitest：月份边界、当月接取上限、跨月保留、库存校验零消耗、交付只奖励一次、放弃无惩罚、迁移和导入非法状态。
- 平衡模拟：比较启用委托前后的定额达成率、灵石/贡献/心得曲线与筑基时间。
- 手工验证：接受委托→种植/收获→交付→月末定额；刷新与导入后继续；库存不足与放弃路径。

## 6. 待确认与实施依赖

- 需求文档列出的每月选项数、接取限制、现有库存交付和奖励池需用户确认。
- 数值确认后才能进入阶段 1；界面原型另有一次用户确认门控。
- 委托实现服务需等 T33 的 v4 存档迁移落定后再改存档链。
